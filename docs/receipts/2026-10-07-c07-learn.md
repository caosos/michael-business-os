## What it does
- **Read.** `learn.load_outcomes(conn)` reads Outcome v1 documents from Agent 04's `mbos.v_outcome_documents`, and item metadata (category, condition, source) from `mbos.v_item_documents`. It issues SELECT statements only, through any DB-API connection with the read role; a test asserts it only reads. Callers may also pass Outcome v1 dicts directly, for example through 04's State MCP (D-06).
- **Calibrate.** `calibrate()` computes Brier scores for probability fields (repair, sale, win, completion) and MAPE plus bias for continuous fields, per field and per group. Groups are flip `category/condition`, service `category`, and lead `source` for win probability.
- **Propose.** `propose_learn_bump()` applies deterministic rules. Parameters are in priors 2026.10.2 `learn` (REC):
  - Probabilities: beta-binomial shrink of the current prior, weight 10.
  - Labor hours: the prior × the shrunk actual/predicted ratio.
  - A change is proposed only when the group has n ≥ 2 and the relative change is ≥ 2%.
- **Output.** The next estimation-priors document (version+1, changelog), its diff, and a **tier-0 ActionRequest draft**:
  - capability `config.scoring.bump`, `status: drafted`, reversible
  - `payload` = {target, versions, diff, rationale, evidence_refs (outcome ids), the **entire** proposed document, document_hash}. The payload hash binds Michael's approval to exact content.
  - `verify_proposal()` lets the gateway or UI re-check both hashes.
- **Provenance.** One record per run: tool `mbos_economics.learn`, `inputs_used` = each outcome's content hash plus the priors hash, `derived_from` = the outcomes' provenance.
- **Apply path** (not in this task): on Michael's YES, the State lane archives the current file to `config/history/`, writes the new one, and emits `CONFIG_VERSION_BUMPED`. This is unchanged from ADR-03-002 §6.
