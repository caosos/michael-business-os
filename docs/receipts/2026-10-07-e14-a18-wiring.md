## Built (`mbos_governance.spine_adapter`)
- `build(dsns, policy_path=None, *, dbos=None, egress_file, litellm_file)` wires the three hooks (`DbosCancelHook`, `EgressPolicyHook`, `LiteLLMBudgetHook`), so an engage runs them.
- `engage_panic` / `release_panic` / `panic_state` are plain JSON-returning functions. A release runs as the `approver` role, and an engage never raises for a database outage.
- `schedule_reconcile(gov, DBOS, crontab, name)` returns a `ScheduledReconcile`:
  - `workflow` is registered before launch
  - `.activate()` creates the persistent DBOS 3.x schedule after launch, and is idempotent
- The L3 cancel hook now has a `protect` set, so the scheduled reconcile runs are never cancelled while frozen.
- The call sequence is documented in `docs/integration/05-spine-adapter-A18-call-sequence.md`.

## Verification (FACT)
- 9 E-14 tests pass. The full suite (371 tests) passes on PG16.
- A subprocess test uses **real DBOS 3.2** with a 1-second cron and a crashed claim. The schedule fires, the claim settles, the crashed-before-send request becomes `failed` with no resend, and `.activate()` returns `created` and then `unchanged`.
- **A correction found by that test.** DBOS 3.x has no `@DBOS.scheduled` decorator (my first draft used it). Schedules are created with `DBOS.create_schedule` after launch. Hence the two-step `schedule_reconcile` + `.activate()`.
